## 音色 ↔ 角色 数据模型诊断（第五轮 · 用户追问「音色和角色什么关系」）
**结论：设计上二者无从属关系（音色是独立声源资产，角色靠选角引用，且按年龄阶段 1:N）；实现上被做成了「角色的一个属性」，靠一次性批量写入同步，且写错。**

### 真实三层链路（已逐行核对）
- `characters` ——(voice_profiles.character_id, 0..N，NULL=旁白)→ `voice_profiles`（独立声源：provider+model+voice_id/voice_asset_id+speed/pitch/style+age_stage）
- `voice_profiles` ——(segments.voice_profile_id)→ `segments`
- `segments.character_id` 只用于 UI 显示与批量范围，**不参与合成解析**

### 三个机制性硬伤
1. **改角色音色 = 分段引用被清空，不是改指新档案**
   - `set_character_voice`（lib.rs:1496-1522）：先 upsert 档案（新档案 `age_stage` 硬编码 `'adult'`），随后
     `UPDATE segments SET voice_profile_id = NULL WHERE character_id=?1 AND audio_status='missing'`
   - 注释写「未生成音频的分段跟随新音色」，代码实际是**清空**；且前端 `setCharacterVoice`（useStudioActions.ts:106）**没有**补调 bind
   - ⇒ 改过音色的角色，其未生成分段下次合成 JOIN 不到 profile → `COALESCE(v.tts_provider,'mock')`（tts.rs:928）→ **变 mock**
   - ⇒ 已生成分段则保留旧 profile_id，且非 force 时被 `filter_tts_requests` 跳过 → **音色不变**
   - ⇒ 这正是此前 26 段 `voice_profile_id=NULL`/mock 的机制性来源；上轮用脚本补数据只是止血，**改一次音色就复现**
   - 正确的 `bind_voice_profile_to_matching_segments`（tts.rs:580，带 replace_existing 开关）**前端零引用，从未被调用**
2. **年龄时间轴在运行时完全不存在**
   - `load_tts_requests`（tts.rs:928-934）只 `LEFT JOIN voice_profiles v ON s.voice_profile_id = v.id`，**不读 age_stage**
   - `preferred_voice_profile_for_character`（tts.rs:644）排序为 `CASE provider='mimo' THEN 0 ELSE 1, name`，**不看 age_stage**
   - `segments.age_progress`（REAL，storage.rs:144）字段存在但**无任何查询读取**
   - ⇒ product-brief 第 6 节「童年→老年按阶段换音色」只有存储字段 + VoiceCenter 的标签，链路未落地
3. **UI 把 1:N 拍平成 1:1，且分段实际引用不可见**
   - `Inspector.tsx:127` `profiles.find(v => v.characterId === character.id)` 只取第一条 → 一个角色一个音色
   - 分段行不显示 `voice_profile_id`，用户无法看到「这段实际会用哪条档案」
   - ⇒ 存在三套可互相分叉的真相：角色卡片显示的音色 / 声音中心列出的档案 / 分段实际引用的档案

### 方案影响
- 此前提出的「把角色声音工坊入口从 `stability==='design'` 解绑」**建立在错误抽象上**（把音色当角色属性），暂缓
- 正确顺序：先摆正模型 —— 音色提升为一等资产、角色↔音色是选角关系（角色×年龄阶段）、分段引用可见且可校验；`set_character_voice` 改为「重放引用」（调 bind 而非清空）；生成前校验空引用 fail-closed，取代 mock 兜底
- 用户尚未确认模型，暂不动手改代码

### 补充核实：代码里「派生模式」已有先例，但与合成链路语义打架
- `update_segment`（lib.rs:394-397）**就是派生模式**：保存分段时按 `character_id` 实时解析
  `tts::preferred_voice_profile_for_character()` 并写回 `voice_profile_id`；选旁白则落旁白档案
- 合并角色（lib.rs:537-540）也是"重放引用"：`UPDATE segments SET character_id=?, voice_profile_id=? WHERE character_id=?`
- 但合成链路 `load_tts_requests`（tts.rs:932）**只 JOIN `s.voice_profile_id`，完全不看 `character_id`** = 副本模式
- ⇒ 同一份数据上两套语义：**派生只发生在"编辑那一次"，之后冻结成副本**；任何不经过编辑的动作
  （标注、改角色音色、脚本直改）都不会刷新副本 → 副本脱钩
- ⇒ 与 `set_character_voice` 的置 NULL（lib.rs:1520）直接打架：编辑写对 → 改音色清空 → 合成变 mock
- **暗雷**：`update_segment` 中若该角色**尚无音色档案**，`preferred_voice_profile_for_character` 返回 `None`
  → 直接写 NULL → 合成即 mock。即「把分段绑定到还没定音色的角色」= 静默变 mock
- **一致性结论**：应确立「角色(×年龄阶段) = 唯一权威，分段 = 派生视图」，`segments.voice_profile_id`
  仅保留一个用途 —— **冻结历史版本**（product-brief 第 6 节：单段返修须继承生成时的音色阶段，
  不能拿"当前"音色去修旧段）。当前把"覆盖/冻结"当成了默认，才是脱钩之源。
- 改造第一刀（待用户确认）：① `set_character_voice` 删掉置 NULL 动作；② `load_tts_requests` 改为
  回退解析（优先分段冻结 → 否则按 character_id + age_progress 解析角色权威音色 → 都没有则**报错而非 mock**）；
  ③ `preferred_voice_profile_for_character` 增加 age_stage 维度（当前只按 provider/name 排序）；④ 分段行显示实际解析到的音色

## ⚠️ 第六轮 · 更正第五轮的模型判断（用户追问「直接为角色生成音色？声音库不一定有必要」）
**第五轮那句「设计上二者无从属关系，音色是独立声源资产、可跨角色复用」是我自己加的抽象，product-brief 里没有。以纲领为准，该判断撤回。**

### 纲领原文（`docs/product-brief.md`）
- 第 4 节 Core Data Model：`VoiceProfile: character ID, age stage, TTS provider, voice ID, speed, pitch, timbre/style settings.`
  → **VoiceProfile 的第一个字段就是 character ID**，音色本来就是**从属于角色**的，不存在独立资产池这层抽象。
- 第 3 节 MVP Workflow 第 5 步：`Assign each character a human CV, TTS voice, or voice profile.` —— 每个角色过一遍音色。
- 第 6 节：一个角色按 age_stage 可绑**多条**音色（1:N），但都归属该角色。

### 确立模型（角色 = 音色唯一归属）
- `characters` 1:N `voice_profiles`（按 age_stage）；**不存在「独立可浏览的声音库」实体**
- `segments` 只记 `character_id` + `age_progress`，合成时**实时解析**出音色；`voice_profile_id` 退化为
  「本次生成冻结了哪条」的历史记录（服务第 6 节单段返修须继承生成时阶段）
- 旁白不是特例：给它一个内置角色身份，与角色共用同一套「定音色」面板
- `voice_assets`（克隆参考音频）**保留** —— 它是克隆的**输入素材**，不是音色库
- 群众角色共用 / 跨项目复用：从「共享记录」改为「复制 voice_id 值」+「从其他角色/项目导入音色」动作

### 落地四刀（**用户已确认「开始」，第七轮已全部实现并验证**）

## 第九轮 · 「生成声音试听」报 `error decoding response body`（用户报，已修并联网验证）

### 症状 → 根因链（每一环都实证过）

## 21:22 「当前分段未解决问题」堆了一串 script_changed —— 自动提示的重复累积 + 永不关闭

## 21:24 点分段「播放」按钮只加载不播放，多一步操作

### 用户诉求
分段列表每行的 ▶ 按钮点下去只是把音频装进底部播放器，还得再点一次播放键才开始播。

### 根因
- `useStudioActions.playAudio` 只做 `setAudioPath(path)`；
- `AudioPlayer` 的 `useEffect([src])` 在源变化时**无条件 `pause()` + 归零** ⇒ 新源永远是"已加载但暂停"。
- 两处合起来 = 用户必须再点一次。**"设置状态"和"执行动作"混成了一个**.这是 UI 里很常见的一类缺陷。

### 修法
- `AudioPlayer` 新增 `playSignal?: number` prop：**递增即代表"现在就播"**。
  新增第二个 effect（**声明在 src 重置 effect 之后**，保证"先重置、再播放"的执行顺序），
  内部用 `handledSignal` ref 守住"同一信号只处理一次"。
  换源那次由前一个 effect 归零；同一条再点则 `if (audio.currentTime > 0) currentTime = 0` 从头重播。
- `useStudioActions.playAudio`：拿到 path 后 `setAudioPath` + `onRequestAudioPlayback()`（新参数，由 App 传 ↦ `setAudioPlaySignal(v => v+1)`）。
- 找不到音频时 `setNotice("这个分段还没有可播放的音频，请先重新生成或上传")` —— **不再静默失败**。
- `AudioPlayer` 新增 `onPlaybackBlocked`：`play()` 被拒时给可见提示，而不是无声无息。

### 顺带修的两个不一致
1. **底部播放器显示"正在播的分段"而不是"选中的分段"**：新增 `playingSegment` state，
   `playerSegment = playingSegment ?? selectedSegment`。以前点第 3 行播放、底部却显示第 1 行。
2. `audio::segment_audio_path` 加**文件存在性检查**，文件不在返回 `None`
   ⇒ 前端能给出"没有可播放的音频"，而不是把一个死路径交给 `<audio>` 得到莫名其妙的播放失败。

### 关键事实（已写入 MEMORY.md）
**wry 的 `WebViewAttributes.autoplay` 默认是 `true`**（`wry-0.55.1/src/lib.rs:843`），
且 Tauri 不覆盖它（`tauri-runtime-wry` 里完全没提 autoplay）⇒ macOS 上会执行
`setMediaTypesRequiringUserActionForPlayback(None)`，**不需要用户手势**。
所以"IPC 往返之后再调 `play()`"不会被自动播放策略拦截 —— 这条决定了这个方案可行。
（反面：若 autoplay 为 false，await IPC 后的 play() 很可能因手势失效被拒，那就得换成同步链路。）

### 验证
- `tsc --noEmit` 通过；`cargo test` → **56 passed / 1 ignored**；二进制重建、应用重启（pid 66643，Vite 1420）。
- 纯前端改动走 Vite HMR，Rust 那处（segment_audio_path）需重启。

## 分段输入框加常驻标签（用户报「填了内容就看不出哪个是台词、哪个是情绪」）

### 问题
分段行里「文本域」和「情绪框」都没标签：
- 文本域连 placeholder 都没有，空态就是个无字白框；
- 情绪框的 placeholder 写着「情绪：如 愤怒、温柔、平静…」，**一填内容名字就消失**。
`placeholder` 是空态提示不是标签 —— 这是本次的核心判据。

### 改法（ScriptSurface.tsx + components.css + constants.ts）
- 两个控件各包一层 `.segment-field`（label + 控件 的 flex row），左列标签**常驻**。
- `.segment-field-label`：fs-2xs / text-tertiary / `line-height: 1.7` / `padding-top: 5px`
  —— 5px = 控件 4px 内边距 + 1px 边框，让标签中心与**首行文字**中心对齐；
  多行文本时标签贴顶对齐首行，单行情绪框里自动恰好居中（14px vs 14.35px）。
- 控件改 `flex: 1 1 auto; min-width: 0`。**坑**：原有的 `grid-area: text` /
  `width: auto`（为 grid 布局写的）在变成 flex 子项后全部失效，不显式补 flex 会塌成内容宽度。
- 标签文案取表头同一份常量：复用 `text.content`（"文本"），新增 `text.emotion`（"情绪"）。
  标签化后 placeholder 的重复前缀删掉 → `text.emotionPlaceholder = "如 愤怒、温柔、平静（标注时可自动生成）"`。
- 标签文案选「文本」不选「台词」：类型下拉已经写了"台词/旁白"，旁白行的框里装的不是台词，写「文本」才不会自相矛盾。

### 验证
- `tsc --noEmit` 通过；前端改动走 Vite HMR，真实窗口（1280×860）截图确认 3 行分段
  的「文本」「情绪」标签均在位、与首行对齐、输入框未被挤窄。
- 顺带把这条反向边界补进 skill `card-density-and-inline-hint`：
  **瘦身只能删"解释"，控件的"身份标签"必须常驻**。

## Round 14：插入条的「插入/取消」按钮被顶出容器（2026-09-25 23:03）

### 根因（实测 getBoundingClientRect）
`.segment-insert-bar` 里 SELECT 宽 702（= 整条 bar），按钮 left 983 > box right 984，
scrollWidth 802 > clientWidth 702。
- 全局 `base.css` 表单控件规则：`input, select, textarea { width: 100% }`。
- `.segment-insert-bar select { flex: 0 0 auto }` → basis=auto 解析到 width:100%，
  且 **flex-shrink: 0 不可收缩** → select 独占整行，两个按钮被挤到容器外。

### 修复
`.segment-insert-bar select { flex: 0 0 auto; width: auto; min-width: 96px; }`
—— flex 子项要覆盖全局 width:100% 必须**显式写 width: auto**（不是改 flex 就行）。

### 教训
全局表单控件 `width: 100%` + flex 行布局 = 隐性地雷。凡是把 select/input 放进 flex 行，
都要确认它的 width 是否被全局规则拉满；`flex-shrink:0` 会把溢出变成"顶飞兄弟"。

### 验证
mock：SELECT 96px、按钮 377-419/427-469 ⊂ bar 273-975、overflowX=false、
上排 actions 779-984 ⊂ row 248-1000、doc 无横向滚动。重新 build + 覆盖安装。
