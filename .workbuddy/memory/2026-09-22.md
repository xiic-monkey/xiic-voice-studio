## UI 功能全链路静态审查（排查"点击无效"）

方法（可复用）：不是靠肉眼读代码猜，而是做**可机器验证的交叉核对**。

### 排除项（已验证正常，别再重复怀疑）
1. `pnpm exec tsc --noEmit` 通过 → 无未定义 handler / props 缺失 / 参数类型错误。
2. 前端 invoke 的命令后端**全部已注册**（`lib.rs` generate_handler 共 59 个）。注意：脚本从 `generate_handler!` 提取命令时，若用"逗号结尾"正则，会漏掉**最后一项**（它后面是 `])` 没有逗号）——曾因此误判 `set_narrator_voice` 未注册，实为提取误差。
3. **Tauri v2 的 `#[tauri::command]` 默认 rename_all = camelCase**，所以 Rust 的 `chapter_id` 在 JS 侧就是 `chapterId`，前端传 camelCase 是正确的，不是 bug。
4. **但 `#[tauri::command]` 只管函数参数名转 camelCase，不管结构体内部字段**——请求体结构体必须显式写 `#[serde(rename_all = "camelCase")]`。本项目 `TtsBatchRequest`(lib.rs:112-118)、`TtsTestRequest` 等都写了，已核对无误。
5. `run()`(useNotifier.ts) 的错误会 `setNotice(errorMessage)` → 后端报错用户看得见，**不是静默失败**。
6. `desktopRuntime = isTauri()`(App.tsx:34)，原生窗口恒 true，守卫分支不会触发。
7. 所有返回 StudioSnapshot 的 action 都传了 `project.hydrateSnapshot` 作为 onDone；job 类传了 `setSegmentJobs` → 数据会写回，不存在"改了但界面不刷新"。
8. 各 disabled 条件均为基于真实状态的合理判定，无恒真/恒假。

### 发现的问题（真）
1. **`export_character_script`（导出角色台词本）后端已实现并注册(lib.rs:1272/1829)，但前端 UI 完全没有入口**——导出菜单(ScriptSurface:285-323)只有配音文稿/分段音频/整集/制作包/检查发布 5 项。该功能用户用不到。
   - 且它签名是 `fn export_character_script(state)`，**不接受 `chapter_ids`**，与另外三个导出命令（`chapter_ids: Option<Vec<String>>`）不一致；将来接入也**无法按选中章节范围过滤**。
2. **`regenerate_segment` 是死代码**：后端实现并注册，前端从未调用。UI 的"重新生成"按钮走 `App.tsx:195 → generateTts([id], true) → enqueue_tts_batch(forceRegenerate)`，该链路已验证通畅（`tts.rs:1044` force_regenerate 为 true 时不过滤保护段，`tests.rs:1262` 有单测覆盖）。
3. **`bind_character_voice`  likewise 从未被前端调用**（UI 走 `set_character_voice` / `assign_voice_profile`）。
4. `list_chapters` / `list_segments` / `list_characters` 未被调用（数据经 open_project 的 Snapshot 一次性返回），属合理冗余。
5. **`generateTts`(useStudioActions:285-296) 绕过了统一的 `run()` wrapper**，直接 invoke + catch → 点击生成时**没有 busy 忙碌态指示**，反馈行为与其他 action 不一致（错误仍有提示）。

### 结论
静态层面未发现"某个按钮点击后完全无反应"的机制性断裂。若用户实际遇到某按钮无效，大概率是运行时/数据态问题（无选中章节、无 API Key、供应商配置不符、审听保护等），需在原生窗口实际复现并看日志。
